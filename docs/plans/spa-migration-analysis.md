# SPA Migration — Impact Analysis (companion to `docs/plans/spa-migration.md`)

*This document deepens `docs/plans/spa-migration.md`. The plan states the phasing and the "why"; this is the pre-commitment impact map — what breaks, what stays, and the decisions only the owner can make. It does not replace the plan.*

---

## 1. TL;DR

Yes, this is worth doing — but the value is almost entirely in **Phase C** (the game in the same document), and Phase C is where the real risk lives. The migration's headline unlock is a **single session-long `AudioContext`**: it deletes the per-page audio-unlock retry machine and the Firefox Space-gate outright, and it is the precondition for session-long music/crossfade — the one feature `ROADMAP.md:262-265` and `spa-migration.md:90` both call "the feature that pays for Phase C." It also opens genuinely new modification surfaces the owner cares about: persistent overlays, live mid-race settings, pause→settings/garage→resume, and cross-screen state. **The single biggest danger is not the router — it is engine re-entrancy**: today `location.reload()` is a hidden correctness net that resets a mutable `S` singleton and cone knocked-state that nothing else ever resets. Remove the reload without adding `initState()` + cone reset and **race #2 is broken from frame 1** — and the physics golden-masters will stay green while it is broken. Honest shape: Phase A (extract inline scripts) is low-risk and independently valuable; Phase B (router + menus) is medium; Phase C is the one that needs careful blocker-ordering, a Mali-GPU disposal story, and a manual playtest gate.

## 2. What the migration UNLOCKS (advantages)

### Audio / music — the headline
- **One unlock per session, every browser.** Today `js/sound.js:232-243` registers persistent capture-phase `pointerdown/keydown/touchend` listeners that retry `ctx.resume()` on *every* gesture and re-arm on *every* page load, because activation dies with the document and desktop Firefox never grants it for arrow keys (`sound.js` comment 227-231). One document ⇒ one unlock on the first menu tap; the retry loop and the not-yet-shipped Firefox Space-gate (`spa-migration.md:98-99`) become dead code.
- **Session-long music + menu↔race crossfade.** Impossible today: every page is a fresh `_ctx` (`sound.js:11-12`, discarded on unload). `ROADMAP.md:262-265` marks this explicitly "blocked on the SPA migration." On one timeline this is gain automation on a single node, not a per-page restart.
- **The ~100ms navigation-defer hack disappears.** `soundThenGo`/`tapThenGo` (`sound.js:126-127`) deliberately delay every menu tap so the SFX isn't cut by unload. No unload ⇒ delete the timer ⇒ menus get ~100ms snappier and the cue plays uninterrupted.

### Transitions / performance
- **No white flash between screens** (inference, worth an empirical check in the CrazyGames iframe build): MPA navigation is a full document load per screen (`index.html:104`, `game.html:61,76`).
- **Shared JS parsed once.** `render.js` (39.8 KB) + `game-engine.js` (34.2 KB) headline a game closure re-parsed on every restart via `location.reload()` (`game-engine.js:316`, `race-results.js:44`). Parsed once per session in the SPA. (Absolute KB shrink under minified `dist`; the re-parse-per-nav pattern is what goes away.)
- **Warm/prefetched track imports.** `game.html:68-73` does `await import('./js/track-${id}.js')` (with an SVG fetch) only *after* the user leaves the menu. A resident shell can prefetch on card hover so Race starts with no load gap.

### New MODIFICATION capabilities (most important to the owner)
- **Persistent overlays above all screens.** Deletes the achievement-toast `sessionStorage` relay that exists *only* to cross a page boundary: `queueAchievementToasts`→`sessionStorage` on buy (`ach-toast.js:23-30`, called `modify.html:468`), `flushAchievementToasts` rehydrates on the next document (`ach-toast.js:33-40`, called `select.html:372`). One document renders the toast in place. Generalizes to wallet/streak/notifications.
- **Live settings mid-race.** Units are read once at startup and frozen (`game-engine.js:342-344`, `isMph` const); reaching settings today means leaving the race. A pause→settings→resume overlay can re-read units and relabel `#spdUnit` (`game-engine.js:346-347`) without ending the run. (Volume/soundEnabled are *already* live — `sound.js:22,59`.)
- **Pause→settings/garage→resume without losing the race.** Today the only exits from a live race are hard: `location.href='index.html'` (`game-engine.js:315`) or `location.reload()` (`game-engine.js:316`). `pause.js` already freezes the loop and releases steering (`pause.js:36-42`); an SPA can overlay UI on the paused-and-resident engine and resume the exact state.
- **Global reactive state without a reload.** `profile-sync.js:63` forces `location.reload()` after import "so every module re-reads the save." A store change-bus (or a screen re-mount) lets import/purchase/unlock effects propagate live.
- **Cross-screen / shared-element animations** (car flies from garage into the race) — unavailable across a document boundary.

## 5. Decisions & remaining questions

**Owner decisions (2026-07-15):**

1. **URL scheme → hash routing.** `#/game?track=x` in the address bar is acceptable; no History API. (This also sidesteps the no-404.html / sandboxed-iframe problems for free.)
2. **SEO / old URLs → not a constraint.** The game is early-stage with effectively no external inbound links, so preserving `game.html?track=` / `sandbox.html` / `donate.html` as physical files is a courtesy, not a requirement. Redirect shims are optional and low-priority; the router does not have to honour old URLs.
3. **Music → wanted, "nice to have".** Phase C is therefore justified but **not urgent**: A and B ship on their own value, and C waits until music is actually being built. Music is what pays for C, so C's trigger is "we're doing music now."
4. **Ad-mute → shared-context freeze is the intended behaviour.** Muting/pausing audio during an ad is standard (and portal-required); routing music through the same master bus means the existing `setMuted`→`suspend()` freezes it for the ad and resumes after — for free. Music must **not** be a separate `<audio>`/context (that would play over the ad). ⚠️ **No portal is live yet** (CrazyGames not set up), so this is *design-it-right-now, verify-when-a-portal-exists* — not a current gate.
5. **Playtest → in hand.** The owner already playtests each change, so the 20-restart Mali heap gate fits the existing loop. The "verify on a real CrazyGames ad" step is deferred until a portal exists.
6. **Risk mitigation → TDD-first (see §6, Phase C.0).** Since the risk concentrates in Phase C and the blockers are pure-logic re-entrancy bugs, write the re-entrancy tests before touching the engine.

**Still open (implementation-time choices, not blockers):**

- **ASSETS list:** auto-generate from the file tree (recommended — removes the atomic-`addAll` hazard for both add and remove) vs a `js/*.js ⊆ ASSETS` test. Exclude `platform-*.js` and `car-registry.js`.
- **`createTrack()` fork** (risk #3): parse-once-memoized geometry + fresh per-race cones (recommended) vs re-parse-each-race.
- **Restart back-button:** `replace` (Back skips the finished race — recommended) vs `push`.

## 6. Sequencing recommendation

The plan's **A/B/C phasing is correct** — keep it. Refinements:

- **Phase A (extract inline scripts → `js/screens/*.js`) delivers real value even if C never lands.** It removes per-page boilerplate and is low-risk. **Gate A on: every screen returns a real, no-op-safe `destroy()`** (cancel rAF, unsubscribe, remove window listeners, remove body-state classes) *now* — otherwise Phase B is a second rewrite of the same files. Sequence by teardown risk, not size: **zen / settings / achievements first** (grep-verified leak-free — build the harness), then **tracks**, then **select and modify last** (they carry the window-listener / uncancellable-rAF / shared-`CARS.body` debt the harness must prove out). Extract `drawThumb`+`TRACK_GU` byte-for-byte first (`tracks.html` / `zen.html` are byte-identical), dedupe as a follow-up so any render delta is bisectable.
- **Phase B (router + menus)** is medium-risk and mostly mechanical: one `parseRoute(url)` covering the **fully enumerated** param vocabulary (`track`, `mode=zen|sandbox`, `dir=rev`, `car`, debug `dpr`/`surface` — readers only at `game.html:54-57`, `select.html:64-68/149`, `modify.html:126-127/132`, `render.js:46/132`). Keep old `.html` as thin redirect shims during a transition window. Move `sw-update` suppression to engine state here (risk #6). Correct the fact bug: reversed is `dir=rev` in URLs; `:rev` is only the store key (`track-util.js:296`) — a router that greps `:rev` in the URL silently loads forward.
- **Phase C.0 — write the re-entrancy test harness FIRST (TDD; owner's call).** The Phase-C blockers are *pure-logic* re-entrancy bugs that the golden-masters miss (they run one race), which makes them ideal TDD targets. Extract `initState(S)`, `resetCones(cones)`, and the `reverseTrack` deep-copy as pure functions, then write **failing** tests and implement to green: "two `initState` calls leave every `S` field at its default"; "a knocked cone is un-knocked next race"; "mutating a reversed track's cones does not touch the forward array"; "a key held down at `stop()` reads `false` on the next `startGame`"; plus `parseRoute(url)` cases. These can land as **standalone hardening before the router** — they fix latent bugs reload masks today and de-risk C independently. **Honest limit:** TDD covers the pure re-entrancy + routing logic only. The DOM/RAF/AudioContext lifecycle, heap flatness across restarts, and Mali GPU-disposal are **not** unit-testable — they still need in-browser instrumentation + the manual playtest gate. Green tests cover the half the golden-masters don't; they do **not** mean Phase C is safe.
- **Phase C (game in the shell) is the dangerous one — order the blockers:**
  1. **`initState(S)` + clear `keys`/`pointers`** (risk #1) — nothing else works until this lands. (Test-driven per C.0.)
  2. **Cone reset + `reverseTrack` deep-copy** (risk #2) — independent of, and required alongside, the factory decision.
  3. **`createTrack()` fork** resolved (risk #3): parse-once geometry, fresh mutable state per race.
  4. **Restart = route re-mount, not `location.reload()`** (risk #10), deferred out of the click handler (risk #11), with the `race-results` overlay destroyed first (risk #4).
  5. **`render.init/dispose` + Mali `disposeRender()`** (risks #5, #13) — the owner's active GPU concern; verify across the 20-restart heap gate.
  6. **Music routing decision** (risk #9) gated before session music ships.

Keep `stopDrift()` unconditional in every teardown path and **do not** re-add a context-killing `suspend()` on exit (the stale `sound.js:211` comment invites exactly that regression — session music wants the context alive). Keep `__ddActiveGame` — it becomes *more* valuable in the SPA, not MPA cruft.

Net: **A is safe and useful standalone; B is a bounded router wire-up; C is worth it only if music/the new modification surfaces are genuinely wanted, and only with the six blockers above ordered as listed.** The physics core, saves, build, and platform adapter are provably untouched — the blast radius is small and lives almost entirely in the engine's (re)init side, which the plan under-specifies today.
