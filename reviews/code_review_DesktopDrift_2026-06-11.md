### Главные сильные стороны
- **Ацикличный DAG модулей** (проверено: циклов нет), pure-логика (`scoring.js`, `track-util.js`) вынесена из closure и покрыта юнит-тестами.
- **Образцовый lifecycle движка**: `startGame()→{stop}`, все слушатели через единый аккумулятор, реентерабельность, анти-дубль-rAF через `globalThis.__ddActiveGame`. *(Закрывает находку прошлого ревью про утечки.)*
- **Реальные перф-оптимизации v42**: кэш `Path2D` статики/миникарты, батч скидов по 6 уровням альфы, локальный поиск ближайшей точки центра O(N)→O(49).
- **Единая точка персистентности** (`store.js`) и самодостаточные UI-компоненты (`pause`/`confirm-exit`/`race-results`).

### Главные риски
1. **🔋 Батарея на мобиле** (жалоба владельца) — нет FPS-cap (на 120 Гц телефоне рендер ×2) + регрессия по конусам (×3 заливки) + shadowBlur. Раздел §4.
2. **🎯 Система очков эксплуатируема** — PPS-рекорд поощряет минимизацию времени, срезание трассы (края трека не сталкиваются), near-miss-фарм. Раздел §6.
3. **📦 Хрупкое обновление PWA** — SWR-рассинхрон html↔js↔css; bump кэша ручной; миграций store нет → будущий bump версии сотрёт рекорды. Разделы §8, §9.

## 4. 🔋 Производительность и БАТАРЕЯ (§4 + вопрос владельца) — **6/10**

> **Это приоритетный раздел** — прямой ответ на «телефон быстро садится, раньше будто было не так».

### ⚡ ТОП-причины разрядки (ранжировано)

**① Нет FPS-cap → на телефоне 90/120 Гц рендер идёт в 1.5–2× чаще нужного.** `game-engine.js:228-229,494`
Физика frame-rate-independent (затухания в степени `dt·PHYS_HZ`), но частота вызовов `frame()` ничем не ограничена и равна нативной частоте дисплея. На современном телефоне (почти все — 90/120 Гц) это **буквально ×1.5–2 к энергопотреблению GPU+CPU** при той же игре. Cap на 60 геймплей не изменит. — **вклад: High · уверенность: High.**
👉 **Самая вероятная причина «раньше было не так»**, если телефон высокогерцовый (или сменился на такой): фон постоянный, не зависит от трассы.

**② Регрессия v26→v42: рендер конусов подорожал ~×3.** `render.js:308-356`
Было: стоячий конус = 2 арки. Стало: **3 заливки** (тень `+2,+2` с альфой + база + блик). При **~146 конусах (steel-kitchen) … ~210 (workbench)** это +1 альфа-заливка (дороже сплошной) на каждый объект **каждый кадр**. Сбитые конусы тоже усложнены (трапеция-тень + тело + полоса). — **вклад: High · уверенность: High.**

**③ Полная перерисовка статики каждый кадр + DPR=2.** `render.js:233-435,12`
Нет дельты/слоёв/culling: фон во весь экран, стол, трасса, ~150-210 **неподвижных** конусов пересчитываются заново каждый кадр. На retina-DPR=2 canvas = **4× пикселей → каждая заливка ×4**. Фон-`fillRect` во весь мир — самая дорогая одиночная заливка. — **вклад: High · уверенность: High.**

**④ `shadowBlur=14` на чекпоинте каждый кадр — новое в v42.** `render.js:294-303`
`shadowBlur` заставляет растеризовать в отдельный буфер + гауссово размытие — одна из самых дорогих операций Canvas на мобильном GPU. В v26 чекпоинт был простым stroke без тени. Чистая регрессия. — **вклад: Med · уверенность: High.**

**⑤ Неон-glow машины `shadowBlur=22` каждый кадр** (если включён неон в гараже). `render.js:383-406` — существовал в v26 (не регрессия), но в паре с ① удваивается. — **вклад: Med (High при включённом неоне) · уверенность: High.**

**⑥ HUD обновляется через DOM каждый кадр** — 8+ записей `textContent`/`innerHTML` + `lapScores .map().join()` с reverse-копией массива (аллокация строки/кадр). На 120 fps = 120× лишних reflow-триггеров. `render.js:411-428` — **вклад: Low-Med · уверенность: High.**

### Регрессия v26→v42 (git-diff `cfaf107..3574eda`) — баланс
**Подорожало:** конусы ×3 (②), `shadowBlur` чекпоинта (④), шашечный флаг финиша ~40 `fillRect`/кадр вместо dashed-линии (`render.js:268-289`).

**Вывод:** по «числу операций» регрессия скромная (кэш Path2D её частично компенсировал). **Но это не отменяет ① — отсутствие FPS-cap, дающее ×2 на высокогерцовом телефоне на ровном месте.** Если ощущение «раньше не так» совпало со сменой/обновлением телефона на 90/120 Гц — это объясняет жалобу полностью.

## 6. Система очков (§6) — баланс **4/10**, эксплуатируема

Формулы (`scoring.js`) аккуратны и протестированы, но **интеграция в кадре оставляет дыры**. Структурная первопричина: **рекорд трассы = `bestPPS` (очки/секунду), а не время и не суммарный счёт** (`game-engine.js:457-464`) — это переворачивает Time Attack: выгодно минимизировать знаменатель (время), а не ехать быстро-и-чисто.

### Сценарии абуза (пошагово)
1. **[КРИТ] PPS-рекорд несравним и выбивается срезанием.** Меньше дистанция → меньше время → выше PPS при том же combo. Метрика не монотонна ни по «быстро», ни по «красиво». `game-engine.js:449-464` · → хранить рекордом **время круга** или **bestScore**, не частное.
2. **[ВЫСОК] Бесконечное комбо.** Пока `drifting&&onTrack&&crashCd<=0`, банк растёт без потолка длительности (множитель упёрт в 8, но сами очки — нет). На sandbox (`laps=0`) — буквально бесконечный фарм восьмёркой. `game-engine.js:393-409` · → decay после N сек / потолок банка.
3. **[ВЫСОК] Near-miss фарм об один объект.** `+0.28` к множителю с кулдауном всего 0.6 с за нахождение в полосе 42 гу от **любого** конуса/стены. Кружа вдоль ряда конусов — множитель в потолок за ~17 проходов и держится. `game-engine.js:404-405,88-118` · → кулдаун привязать к id объекта.
4. **[ВЫСОК] Срезание трассы — края трека не сталкиваются.** `inner`/`outer` только для отрисовки; combo сгорает лишь при `distTrk>360 гу`. Можно срезать по «газону» в коридоре до 360 гу, не теряя combo (питает сценарий 1). `game-engine.js:386-390` · → коллизия о края трассы ИЛИ жёсткий off-track при `distTrk>TRACK_HALF`.
5. **[СРЕД] «Почти на месте».** Дрифт требует `speed>90` (вращение строго на месте очков не даёт — закрыто корректно), но порог низкий → плотные медленные круги долго копят combo. `scoring.js:28-29`.

**PPS-деление на ноль** защищено тестом. **Reversed-режим** не реализован (кнопка `disabled`) — асимметрии направлений пока нет, но и пункт ТЗ закрыть нельзя.

- **Для игры — N/A.** DesktopDrift — статический client-only сайт на GitHub Pages, **своего HTTP/2-сервера не держит**; за инфраструктуру Pages (включая терминацию HTTP/2) отвечает GitHub. Уязвимость затрагивает серверные реализации (nginx, Apache httpd CVE-2026-49975, IIS, Envoy CVE-2026-47774, Cloudflare Pingora). **В коде игры чинить нечего.**
- **Hetzner `178.104.147.177` (read-only проверка, отдельно от игры):**
  - nginx **1.24.0** (Ubuntu 24.04 LTS), пакет `1.24.0-2ubuntu7.8` (доступен апдейт `7.11`).
  - **HTTP/2 нигде не включён**: директивы `http2` в конфиге **нет**, `listen 443 ssl` закомментированы, TLS не настроен — сайт отдаётся по HTTP/1.1 (порт 80).
  - **→ Поверхность атаки HTTP/2 Bomb отсутствует** (нет активного HTTP/2; браузерный HTTP/2 вообще требует TLS, которого нет). Эксплуатировать нечего.
  - **Рекомендации (гигиена, не срочно):** (1) накатить штатный апдейт nginx `7.8→7.11` (`apt update && apt upgrade`); (2) **если** в будущем включишь HTTPS+HTTP/2 — держи nginx на свежем патче и рассмотри лимиты потоков; (3) отдельно от этого CVE: сайт сейчас без TLS — для статики приемлемо, но HTTPS стоит завести при случае.

### 15.1 FPS-cap на 60 (①) — главный энергетический выигрыш
```js
// game-engine.js, в startGame closure
const FRAME_MS = 1000 / 60;          // целевой кадр
let lastDraw = 0;
const frame = (now) => {
  rafId = requestAnimationFrame(frame);          // планируем всегда
  if (now - lastDraw < FRAME_MS - 0.5) return;   // пропускаем лишние кадры на 120 Гц
  lastDraw = now;
  let dt = (now - last) / 1000; last = now;
  if (dt > 0.05) dt = 0.05;
  // ... существующая логика ...
};
```
**Компромисс:** физика уже FPS-независима (затухания в степени `dt·PHYS_HZ`), поэтому cap на 60 геймплей не меняет; на 120 Гц экономит ~половину работы GPU. Альтернатива «честнее» — фиксированный шаг физики + интерполяция рендера, но это крупный рефактор; для аркады cap достаточно.
